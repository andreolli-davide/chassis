publication controls pass their gates. On 2026-09-22, the maintainer approved

The changelog is dated 2026-09-22; it must be updated if publication moves to a
later day. Any subsequent candidate commit must rerun affected gates before

## Candidate scope

`1.0.0b1` is a contract-review release, not a new execution framework. Relative
to 0.9.1 it deliberately changes no runtime API behavior and increments no
persisted-format version. It adds release controls and review baselines:

- canonical PEP 440 package version `1.0.0b1`;
- supported Python versions 3.12 and 3.13, with newer interpreters excluded
  from beta package metadata;
- a candidate public-API baseline while preserving the released 0.8.1 check;
- deterministic candidates for snapshot, replay, configuration, planning,
  reconciliation, config-apply, and generation-pressure documents;
- a release workflow that calls the complete branch-CI matrix, builds once, and
  promotes the same wheel and sdist bytes;
- prerelease-aware GitHub release semantics and stable-documentation isolation.

The [migration guide](migration.md#09-10-beta) therefore records **no required
application migration**.

## API and format review

### Public API

- `tests/compat/public-api.json` remains the classification source of truth.
- `tests/compat/api-baseline-1.0.0b1.json` pins the exact beta candidate.
- `tests/compat/api-baseline-0.8.1.json` remains enforced independently, so the
  beta cannot weaken the compatibility promise by replacing its reference.
- The compatibility checker covers removed and moved names, positional and
  keyword signature breaks, methods, enum values, and public data fields.
- No stable API is removed in this beta; no deprecation window is consumed.

### Persisted formats

`tests/compat/v1.0.0b1/manifest.json` maps every documented format family to a
candidate fixture and version. The generator drives a real harness, replaces
volatile clocks and instance ids, orders set-derived diagnostics semantically,
and records `SHA256SUMS`. CI regenerates the set in memory and compares every
byte.

Snapshot and replay have public readers and prove exact round-trips.
Configuration is parsed and retains its values while public diagnostics expose
only configuration keys. Planning, reconciliation, config-apply, and generation
pressure are output contracts; their representative nested shapes are pinned.
The released 0.8.1 fixtures still migrate with their documented attribution.

These are explicitly **candidate** fixtures. Final 1.0 must regenerate the
reviewed implementation and check in permanent baselines rather than relabel
the beta directory.

## Publication architecture review

The release path now has one promotion chain:

1. `prepare` verifies version, changelog, and tag agreement;
2. `quality` calls `.github/workflows/ci.yml` from the same commit;
3. CI runs Python 3.12/3.13, coverage floors, minimum/latest dependencies,
   Ruff, Pyright, the full suite, strict docs, dependency audit, wheel/sdist and
   every optional-extra smoke, quickstart, and production reference app;
4. the package job uploads `verified-distributions` only after its smokes pass;
5. `bundle` downloads those exact files, verifies versioned filenames, records
   SHA-256 digests, generates the SBOM, and uploads one `release-bundle`;
6. PyPI and GitHub download that same bundle. Neither rebuilds it;
7. a prerelease is marked as such and cannot deploy the stable documentation;
8. a dry run executes through bundle assembly but cannot publish.

Repository tests pin these dependencies so removing a required job, rebuilding
inside the release workflow, changing artifact names, or allowing prerelease
docs deployment fails the suite. The first hosted candidate exposed GitHub's
static permission validation for a nested, dormant Pages deployment job. Commit
`e16780b` separated the read-only strict-docs quality gate from the deployment
workflow. The subsequent hosted CI and release dry run both passed without
granting Pages or OIDC write permission to CI.

The downloaded `release-bundle` contains only the expected `1.0.0b1` wheel and
sdist under `dist/`, `SHA256SUMS`, and a CycloneDX JSON SBOM. Both distribution
digests verify. PyPI publication, GitHub Release creation, and documentation
deployment were all skipped by the dry run.

## Beta support and incident handling

Until the support decision blocker is closed, the authoritative security policy
remains [SECURITY.md](https://github.com/andreolli-davide/chassis/blob/main/SECURITY.md):
0.9.1 is the supported stable release; 1.0 betas are evaluation releases and
receive fixes in a later beta or final release. The beta never replaces stable
documentation.

For a bad beta publication:

1. do not overwrite or reuse the published version;
2. mark the GitHub release as withdrawn and state the affected versions and
   reason without exposing vulnerability details prematurely;
3. yank the PyPI release when installation would be unsafe or materially broken;
4. preserve the tag and artifacts as provenance unless credential exposure or a
   platform incident requires coordinated removal;
5. fix forward as `1.0.0b2` (or a later prerelease), rerun the complete matrix,
   and link the superseding release;
6. stable documentation remains on 0.9.1 throughout.

Security reports continue through private GitHub advisories. A suspected secret
leak or policy bypass blocks publication and triggers the security process; it
is never accepted as a beta limitation.

## Deliberate limitations

The established design limits remain unchanged:

- plugins are trusted in-process code; policy is not a sandbox;
- replay covers Chassis-owned boundaries, not arbitrary clocks, networks,
  filesystems, or databases;
- wall-clock budget enforcement is cooperative unless Chassis owns the
  cancellable boundary;
- the control-plane resolver has the documented large-composition scaling limit;
- timing and scheduling beyond the documented generation and transactional
  guarantees are not stable contracts.

These are product boundaries, not reasons for NO-GO. The blockers in the
[Decision](#decision) section are release-process gaps and must be closed or
explicitly dispositioned.
